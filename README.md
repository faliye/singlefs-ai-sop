# singlefs-ai-sop-zh

**贡献者治理规范与门禁工具（Contributor Governance），独立分发。**

**它管的是「项目怎么和 AI 协作」**——提交要带什么证据、文档怎么写才不会被检索误读、
决策记在哪、门禁拒绝时必须给出什么。这些与被做的是什么系统无关。

> **实现上 AI 友好，审核上人类友好。**
>
> 这是整套规范的组织原则，展开见 [rules/engineering-philosophy.md](rules/engineering-philosophy.md)。

接入的项目把这个仓库克隆到自己的 `.claude/singlefs-ai-sop/`，于是每个参与者拿到**同一份**规矩、
**同一套**门禁脚本、**同一批** skill。一致性靠共享同一个源保证，不靠各自抄。

**不管的是：某一类系统该怎么设计。** 只有一类项目才需要的纪律
（例如文件系统的「从事务开始」「记账是事务的副产品」）属于项目本地，
放项目自己的 `.claude/rules/`。判据是「**别的项目会不会也需要它**」，
而这里的「别的项目」指任何用这套 SOP 的项目，不是「同类项目」。

## 本仓的变更门槛

**这份 SOP 定下来之后应当几乎不动。** 它是所有接入项目共用的地基，
改一条等于同时改掉每个项目的下限——所以改它的门槛要高于改任何一个项目。

| 想加/改一条 | 先过这三关 |
|---|---|
| 1 | **跨项目通用吗**——任何用这套 SOP 的项目都需要它，不是「同类项目都需要」。只对一类系统成立的，落点是项目自己的 `.claude/rules/` |
| 2 | **能变成一个会失败的检查吗**——变不成的先留在项目 kb 里当待议，不写成规矩（[rules/sop-first.md](rules/sop-first.md)） |
| 3 | **写得出拒绝时的下一步吗**——每条 `bad` 都要带 `howto`，由 `scripts/gate-lint.sh` 强制 |

**这三关靠人判断，不靠门禁。** SOP 是准则，不是被测对象——它该不该收一条规矩，
是只有人能做的判断（[rules/show-me-test.md](rules/show-me-test.md)：门禁证明证据要求，不证明语义正确）。
真正的信号是**改动频率**：这份东西经常变，说明它的设计有问题，而不是说明它在进步。

**作业不在本仓。** 日常工作在接入的项目里——设计决策、不变量、实验、项目本地规则，
全都在项目自己的 `.claude/` 下。本仓只在真要改规矩时才动，那种时候应当很少。

**版本号约定**：`0.x` 表示尚未定型，随时会改，接入方要跟着动。
到 `1.0.0` 之后，`rules/` 的改动应当罕见——多数「想加一条规矩」的冲动，
正确的落点是项目本地。

改了 `rules/` 或 `scripts/` 就抬 `VERSION`：下游项目下次跑门禁时靠版本戳发现规矩变了，
不抬版本 = 别人无从知道。改了 `rules/` 还要重译，三份文本同版本，由 `scripts/i18n-sync.sh` 判。

**多语言只是分发形式，不是几套规范。** 接入的项目只装其中一份，
不需要知道别的版本存在。

## 已知使用者

| 项目 | 位置 | 怎么接的 |
|---|---|---|
| **singlefs** —— 从零设计的 COW 文件系统，Rust 实现 | 本仓的兄弟目录 `../singlefs` | `.claude/singlefs-ai-sop/` 是本仓的副本；项目本地规则在 `.claude/rules/fs-design.md`，设计决策在 `.claude/kb/decisions.md` |

装了之后项目根会有 `.singlefs-ai-sop-version`，门禁比对它和本仓 `VERSION`——
两边对不上就红，提醒那个项目：规矩变过了，先读再跑。

## 里面有什么

| 目录 | 内容 |
|---|---|
| `CLAUDE.md` | **共享规范正文。** 对话语言、文档铁律、Show me test 准入铁律、测试纪律、命令规范、分工判据 |
| `scripts/` | **门禁脚本。本仓库最重要的部分**，规矩的可执行形式 |
| `skills/` | Claude Code skill：怎么跑门禁、怎么记决策、怎么做崩溃测试 |
| `templates/` | 项目侧 `CLAUDE.md` 与 `kb/` 的骨架 |
| `VERSION` | 规范版本号。门禁会检查目标项目声明的版本是否与本包一致 |

## 装到一个项目里

```bash
cd <你的项目>
git clone https://<host>/singlefs-ai-sop-zh .claude/singlefs-ai-sop
bash .claude/singlefs-ai-sop/install.sh
```

`install.sh` 做三件事，**每一步都会回读验证，失败即非零退出**：

1. 在项目根写 `CLAUDE.md`（若不存在），内容是一层薄壳 + 指向共享规范
2. 建 `.claude/kb/` 骨架（若不存在）
3. 在项目根写 `.singlefs-ai-sop-version`，记录当前规范版本

**已存在的文件一律不覆盖**，只报告差异。

## 为什么规范要独立成仓

因为 [rules/show-me-test.md](rules/show-me-test.md) 那条准入铁律——**判据是自动化验证**——
只有在所有人跑的是同一套门禁时才成立。各项目各自维护一份 `.claude`，
三个月后就会出现"我这边是过的"，那条铁律当场失效，
**提交者也就无从知道自己该验到什么程度**——而那正是门禁要替他们回答的问题。

## 多语言：按自己的语言选用

**开发者按自己的语言选用对应版本**，目前有中文、英语、日语，更多版本开发中，
默认版本是英语。装哪种语言的仓，就用那种语言作业——用中文的不必学英文，
用日文的不必读中文。**AI 也不必再翻译一道**：它在哪种语言的仓里工作，
就用那种语言协作，少一次转述就少一次信息损失。这是多语言存在的全部理由。

`I18N` 里 `this=` 是本仓的语言，`default=en` 是默认版本，
`languages=` 是已发布的语言；清单与门禁脚本放在中文仓。

**当前状态：中文之外的版本是机器翻译，为的是快速铺开。** 规范定版前会做精确翻译。

真正消歧的是 `scripts/`：**各语言读法不一致时，以脚本的实际行为为准。**
脚本是这套规则唯一没有歧义的表述，这也是 `sop-first.md`
要求「一条规则要能变成一个会失败的检查」的第二个理由——
**能变成检查的规则，翻译不走样。**

### 一种语言一个仓，目录名统一

```
singlefs-ai-sop-en     英语（默认版本）
singlefs-ai-sop-zh     中文（清单与脚本放在这儿）
singlefs-ai-sop-ja     日语
```

更多语言版本开发中。

声明的语言列在 `I18N` 的 `languages=` 里。各语言不塞进同一个仓——
把 N 种语言塞进同一个仓会让它随语言数线性膨胀，而「薄」正是这个仓的卖点。

项目安装时**只 clone 自己那一种**，目录名统一：

```bash
git clone https://<host>/singlefs-ai-sop-ja .claude/singlefs-ai-sop
```

因为目录名一样，`@` 引用路径和脚本包装**一个字都不用改**——换语言就是换 clone 源。

### 三份必须同步更新

**改了任何一份，其余两份必须一起更新。** 由门禁强制，见 `scripts/i18n-sync.sh`。

对账靠 `MANIFEST.sha256`——`CLAUDE.md` 与 `rules/*.md` 的路径与哈希。
CLAUDE.md 在里面是因为它是规范正文、还规定了对话语言，漏掉它三份会悄悄说不同的话。
其余语言的仓各抄走一份存成 `SOURCE-MANIFEST.sha256`，
之后只要比两份清单，就知道哪几篇落后了。
本仓因此只多**两个小文件**，仍然是单语言、薄的。

改了 `CLAUDE.md` 或 `rules/` 就要跑 `bash scripts/manifest.sh --update`，
否则门禁会红——**清单停滞等于三份都显示「最新」，而其中两份其实已经落后。**

### 一次贡献要覆盖全部已发布语言

**不论贡献者用哪种语言写，提交必须同时改到所有已发布的语言版本，一起合并。**
只带自己那一种语言的提交不收——那等于把「让别的语言的人拿到旧规则」的成本
转嫁给别人。

**各版本说的是不是同一件事，由贡献者自己保证。** 门禁只能看出哪几篇的哈希对不上，
看不出语义是否一致（[rules/show-me-test.md](rules/show-me-test.md)：
门禁证明证据要求，不证明语义正确）。

### 不许只改一份

**改了任何一份，其余各份必须在同一轮里跟上，并更新清单。**

理由是本仓自己的规矩（`kb-discipline.md`）：**矛盾比空白更糟**。
手工维护的多语言规则文件，只要有一次「先改这份、别的下次再说」，
就会分叉——而用另一种语言的人不会知道自己读的是旧的。

**某一份表述不清就改那一份**，并且回头看别的版本是不是也不清楚。
各种语言暴露出来的歧义不一样，这是多语言并存的附带价值，别浪费。

## 更新规范

改 `CLAUDE.md`、`rules/` 或 `scripts/` 必须同时抬 `VERSION`。
各项目 `git pull` 后跑一次 `scripts/gate.sh`，版本不匹配会报出来。
