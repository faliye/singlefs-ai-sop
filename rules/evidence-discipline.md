# 所有结论要三次推导：正推 / 反推 / 校验

**任何结论在说出口之前，必须走完三步，并说清每一步是什么。**
少任何一步，它就叫假设，写成假设，不许写成结论。

| 步 | 问什么 | 做不到就是没做 |
|---|---|---|
| **正推** | 从机制 / 代码 / 数据推到结论 | 说得出「哪条命令、哪几行代码、哪个数据文件」 |
| **反推** | **假设这个结论是假的，那我本该看到什么？** 然后去看 | 说得出一个**具体的、本轮做得到的**观测，以及它没出现 |
| **校验** | 换一条独立路径复现同一个判断 | 两条路径**不共享**同一段代码、同一次采样、同一个工具 |

反推是最常被跳过的一步，而它恰恰最值钱：正推只能告诉你「这个解释说得通」，
反推才能排除「另一个解释也说得通」。

## 一个假设要能被观测否掉，否则它不是假设

写下假设之后，**先问「什么现象会推翻它」**，答不上来就说明它还没成形，不要拿去建实验。

**排除一个假设，要么有可证伪的观测，要么明说是推的。**
「我想不出别的解释」不构成排除。

## 文件系统特有的反推缺口

本工程的多数被测量是**对 / 不对**这样的二值现象。风险不在测量精度，在覆盖：

- **「测试全绿」不等于「实现正确」。** 崩溃窗口可能只有一次写宽，
  没撞上可能只是没遍历到那个崩溃点。要说「崩溃一致性成立」，
  得说清这一轮**本来撞得上吗**——枚举了多少个崩溃点、是不是全部。
- **「checker 没报错」不等于「镜像是好的」。** 也可能是 checker 还没实现那条检查。
  说这句话之前先看 `kb/invariants.md` 里对应条目的实现状态。
