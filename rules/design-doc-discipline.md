# 设计文档铁律

**适用**：README、设计说明、`records/`——**给人通读的东西**。

叙述、论证、上下文是它的职责，不必为机器让路。
写得好读是目标，不是妥协。知识文档另有一套，见 `kb-discipline.md`。

## 1. 正文只写当前现状，历史一律放到文末

不许在正文里出现「原先是 X、现在改成 Y」「以前叫 A」这类历史陈述。
需要保留的历史，一律集中写到文末的「历史版本」一节：

```markdown
## 历史版本

### YYYY-MM-DD
- 曾经 X / 现在 Y / 改动依据：Z
```

**为什么**：正文里混历史，读的人无法一眼分辨哪个是现行值。
叠几轮之后，「当前是什么样」这种最基本的问题都要靠考古才能回答，
而考古出来的结论还经常是错的。这个工程要做好几年，考古成本会指数上升。

**推论**：
- 改了某个决定，**直接改正文**，不要在旁边加注「（原为 X）」。
- 结论被推翻，**删掉正文里的旧结论**，把「曾经 X / 现在 Y / 推翻依据」写进文末。
- 正文里不许出现 `~~删除线~~`、`〔已废弃〕`、`（已被 XX 覆盖）` 这类就地标注。
- 代码注释同理：写「现在为什么这样」，不写「以前怎样」。

`CLAUDE.md` 与 `rules/*.md` **连文末历史版本都不留**，历史外置到 `CHANGELOG.md`——
它们是每次开工都要通读的规矩，混进历史会稀释。

由 `scripts/doc-lint.sh` 强制。

## 2. 长度要配得上改动的重量

论证再扎实，也不构成把它全写出来的理由。
自己觉得「在承重」的那一段，往往正是该砍掉的那一段。
细则见 `writing-economy.md`。

## 3. 该说服人的地方就好好说服

设计文档要回答的是「为什么该这么做」和「怎么上手」。
这两件事需要铺垫、需要例子、需要把取舍讲开——**这些都不是冗余**。

判据：删掉这一段之后，读的人还会不会同意？还上不上得了手？
会 → 可以删。不会 → 它在承重。
