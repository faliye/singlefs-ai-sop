# 说明的长度要配得上改动的重量

**尺子：几行到几十行的改动，commit 正文两段封顶、新增代码注释一行封顶。**
觉得写不下，先怀疑是不是在写不该写的东西。

**删到合适长度是写代码的人的责任，不是 review 的人的。**
论证再扎实，也不构成把它全写出来的理由——自己觉得「在承重」的那一段，
往往正是该砍掉的那一段。

## 不丢内容的前提下，越短越好

**判据：删掉这一句，读的人少知道了什么？** 说不出少了什么就删——
「读着更顺」「显得更周全」不是内容。

啰嗦的代价不是占地方，是**降权**：读的人和检索的模型都要在废话里挑那一句有用的，
挑漏的概率随长度上升。**每一句废话都在给真正的内容降权。**

最常犯的三种，都不是「多写了新东西」：
换个说法把说过的意思再说一遍、给没人质疑的结论加一段铺垫、正着写一遍判据再反着写一遍。

**但短不许拿丢内容去换**——证据、口径、下一步（`sop-first.md` 的 `howto`）一个都不能省。
该留什么见「硬数据不计入尺子」与「删掉这几类」。

### 「越短越好」不是「越短越对」

前一句带着前提（不丢内容），**而前提在传抄时最先掉**——剩下的「越短越好」
会被当成一条可以单独执行的指令，于是每一次删都有了现成的辩护词。

**两个方向的错误不对称，所以拿不准时留着**：啰嗦让内容降权，读的人多花几秒还是找得到；
删过头是内容**消失**，读的人不知道自己少了什么，也就无从要求补上。

走极端的三种形态，每一种都能用「反正更短」辩护：

| 删成了什么 | 丢掉的是 |
|---|---|
| 「实测 3.26×」 | **口径**：什么硬件、什么负载、块大小多少。没有口径的数字不能复核，等于没测 |
| 「不合格」 | **下一步**：`sop-first.md` 要求每条拒绝带 `howto`。删掉它短了，门禁也退回筛子 |
| 「按 D22（单元原子性怎么合成）办」 | **依据**：为什么这么定。三个月后没人知道那句话凭什么成立 |

**反向判据与正向判据成对，两条都要过**：

- 正向：**删掉**这一句，读的人少知道了什么？说不出 → 删。
- 反向：**留着**这一句，读的人多知道了什么？说得出 → 不许删，短了也不行。

## 硬数据不计入尺子

给 review 用的核心实测数据不算在长度里：这类东西 reviewer 拿过去自己就能验，
它是证据不是「请相信我」。

| 不计入（该贴就贴） | 仍计入（先删） |
|---|---|
| 数字：命中/未命中计数、前后对比、耗时 | 这个数字为什么重要、说明了什么 |
| 复现命令 + 它的原样输出 | 我是怎么想到跑这条命令的 |
| 复跑必需的口径：版本、配置、硬件 | 实验历程、试过哪些没用的路子 |

**只贴判决性的那几个数**，完整记录留在 `kb/` 或 `records/`。

## 删掉这几类

1. **主观评价。** 讲自己的观感不算论证，换成能核对的事实。
2. **正文与 kb 重复的内容。** 结论放正文，验证方法放 kb。
3. **旁证。** 需要读者自己补一步推理的证据，换成直接就是结论的那种。
4. **完整的推导链条。** 我是怎么一步步查到的，读者不需要重走一遍。
5. **代码注释里的背景交代。** 注释说明这一行是什么，不承担论证。
6. **为历史辩护。** commit 只写**改了什么**，讨论在上一轮的记录里。
7. **引用的源码。** 读者看得到源码树。日志与 dump 同理，说结论。
   例外是「不贴读者就没法自己验」的判决性证据。
