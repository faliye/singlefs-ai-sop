# 工程理念

> **实现上 AI 友好，审核上人类友好。**

这不是两个目标的折中，**是两条本来就该分开的轴**。

以往它们被混成一条——因为写代码的和读代码的是同一批人，
所以「好写」和「好读」必须是同一件事。**现在不是了。**

## 为什么旧的金科玉律要重新过一遍

现行的软件工程最佳实践，绝大多数是在一个隐含前提下长出来的：
**工程质量的上限由人脑算力决定。**

函数要短、嵌套要浅、概念要少、设计要统一、重复要消除——
这些规矩表面上各说各的，实际上在解同一个问题：**让有限的人脑装得下。**
它们不是错的，它们是**为那个约束校准的**。

而那个约束正在松开。逻辑梳理、一致性维护、穷举覆盖，
恰好是机器的强项，其算力早已越过人脑的上限。

**照着旧极限设的下限，就成了太低的下限。**

所以本工程对既有最佳实践的态度是**思辨地遵守，不是默认地遵守**。
每一条都要重新问：它原本解决什么问题、那个问题今天还在不在。
具体流程见 `machine-first.md`。

## 两条轴各自优化什么

| | **实现面：AI 友好** | **审核面：人类友好** |
|---|---|---|
| 谁在用 | 模型写、模型改、机器验 | 人做判断、人担责任 |
| 优化什么 | 可机检、可穷举、可强制进入、可回退 | 可判断、可信、看得出取舍 |
| 具体形态 | 显式穷举分支胜过聪明的通用路径；类型让非法状态无法表示；不变量写成断言；宁可生成重复也不手工维护 | 决策带依据；门禁失败带下一步；数字带口径；未验证的显式标出 |

## AI 友好 ≠ 不可读

**对模型友好的方向恰好是「更显式」，不是「更晦涩」。**

模型读一段没有命名、没有类型、嵌套七层的代码，处境不比人好——
它拿到的信息更少，出错更多，而且错误更难被发现。
**把可读性砍掉不会让实现更 AI 友好，只会让两边都变差。**

被放宽的只有一样：**为了让人脑装得下而做的压缩**——
比如「一个机制包打天下」「概念越少越好」这类设计层面的统一性要求。

**不在放宽之列**（它们看着像可读性，实际是可验证性或信息量）：

| 项 | 为什么留下 |
|---|---|
| 命名 | **命名是信息，不是装饰。** `fn f(a: u64, b: u64)` 比 `fn commit_txn(gen: Generation, root: Logical)` 少了一整层语义，模型也补不回来 |
| 函数职责单一 | 一个函数做一件**可独立验证**的事——按这个定长度，不按屏幕高度定 |
| **路径数有界** | 穷尽覆盖这段代码要多少个用例？答得出且有界 → 可验证。**注意是路径数，不是嵌套层数**，见下 |
| 约定一致 | 约定不一致会让机械检查失效——这与「设计统一性」是两回事，别混 |

**判据还是那一条**：它让验证更容易，还是只让人眼舒服？
上面这四项都属于前者，所以留下——**理由改写成验证与信息量，不再挂在「可读」上。**

### 嵌套层数本身不设限

「嵌套不超过三层」这类规矩量错了东西。真正决定可验证性的是**路径数**：

| | 路径数 | 可测吗 |
|---|---|---|
| 12 层 `for` 遍历一个 12 维结构 | **1** | 完全可测，深度再大也无所谓 |
| 12 层独立 `if/else` | **2¹²** | 测不完 |
| 3 层独立 `if/else` | 8 | 勉强 |

**循环嵌套几乎不增加路径，条件嵌套按指数增加。** 旧规矩把两者一起限死，
是因为人读起来都一样费劲——那是人的约束，不是验证的约束。

所以：**层数随意，只要（一）路径数说得出且有界，（二）每一层的含义是显式的**。
第二条指的是每层的迭代对象有名字、有类型，不是 `a[i][j][k][l]`——
那种写法的问题不是深，是**不带信息**，与「命名是信息」是同一条。

### 一个例子：语义该放在哪

同一件事的三种写法，从差到好：

```rust
// 一、语义在注释里 —— 传统做法，最差
// dim0: 民族  dim1: 性别  dim2: 年龄段
pop[i][j][k]

// 二、语义在名字里 —— 以往被嫌啰嗦，机器很喜欢
num_china_people[han][woman][teenager_18_to_24]

// 三、语义在类型里 —— 最好，写错维度直接编译不过
num_china_people[Ethnicity::Han][Gender::Woman][AgeBand::T18to24]
```

第一种是**为了让人脑装得下而做的压缩**：名字缩到最短，语义挪进注释。
它在人的时代是合理的——行宽有限、屏幕有限。
但**注释会和代码脱节，名字不会**，因为名字就是代码。

第二种以往常被嫌「太长、一眼能看出是三维数组、何必写全」。
那是人的审美。对机器它是纯增益：每一维自描述，
**不需要上下文就能判断一次访问对不对**。

第三种把信息从「可读」推到「可检」——**维度写反了根本编译不过**。
这与 `machine-first.md`「宁可用类型让非法状态无法表示，不写注释解释约束」
是同一条，也与本工程已定的 newtype 纪律（逻辑地址/物理地址/代号各是一个类型）同源。

**判据**：这段语义放在注释里、名字里、还是类型里？
**越往后越好，因为越往后越难与实现脱节。**

## 推论：人的注意力该花在哪

**人的注意力是这套体系里最贵的东西，所以它不该花在读代码上**——那件事可以交给模型。

它该花在这四件机器判不了的事上：

1. **这个测试测的是不是对的东西**
2. **这条不变量本身对不对**
3. **这个决策的依据成不成立**
4. **要不要接受这个取舍**

四件事都不需要通读实现，但都要求**呈现给人的那一面是人类友好的**。

所以：门禁的输出、kb 的结论、决策记录、失败信息——
**这些要为人优化，而且力度要比过去更大**，因为它们现在是人唯一会看的东西。
把代码写得难读是可以接受的代价；把这四样呈现得难判断不行。

## 两条轴的分界线

> **Gate proves evidence requirements, not semantic correctness.**

这句话就是分界：**机器证明证据要求，人判断语义正确。**
往下是实现面，往上是审核面。
