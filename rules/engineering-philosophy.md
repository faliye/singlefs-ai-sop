# 工程理念

> **实现上 AI 友好，审核上人类友好。**

这不是在两个目标之间折中，而是**两条本来就该分开的轴**。

过去它们是一条，因为写代码的和读代码的是同一批人，「好写」和「好读」只能是同一件事。
现在不是了。

## 为什么老规矩要重新过一遍

现在通行的软件工程最佳实践，多数是在一个没明说的前提下长出来的：
**工程质量的上限，取决于人脑能装下多少。**

函数要短、嵌套要浅、概念要少、设计要统一、重复要消除——这些规矩看着各说各的，
其实在解同一个问题：让有限的人脑装得下。它们不错，只是照着那个约束定的。

而这个约束正在松开。梳理逻辑、维护一致性、穷举覆盖，恰好是机器擅长的，
机器的算力早就超过人脑了。

照着旧极限定的下限，现在就太低了。

「算力超过人脑」这句话靠两条前提撑着，两条都可以被观测推翻：上下文窗口有多大，
以及并发交错能不能穷举判定。前提是什么、口径怎么算、要看到什么现象才算推翻，
写在 `machine-first.md` 的「这条姿态的前提，以及怎么推翻它」一节。
这里不重复——同一条前提写两处，两处早晚说不同的话。

所以对老规矩的态度是**每条都要想过再守，不是照单全收**。
每条都重新问一遍：它当初解决什么问题，那个问题今天还在不在。
怎么问见 `machine-first.md`。

## 两条轴各自优化什么

| | **实现面：AI 友好** | **审核面：人类友好** |
|---|---|---|
| 谁在用 | 模型写、模型改、机器验 | 人做判断、人担责任 |
| 优化什么 | 可机检、可穷举、可强制进入、可回退 | 可判断、可信、看得出取舍 |
| 具体形态 | 显式穷举分支胜过聪明的通用路径；类型让非法状态无法表示；不变量写成断言；宁可生成重复也不手工维护 | 决策带依据；门禁失败带下一步；数字带口径；未验证的显式标出 |

## AI 友好 ≠ 不可读

对模型友好的方向是**更显式**，不是更晦涩。

一段没有命名、没有类型、嵌套七层的代码，模型读起来不比人轻松：它拿到的信息更少，
出错更多，而且错误更难被发现。砍掉可读性不会让实现更适合 AI，只会两边都变差。

放宽的只有一样：**为了让人脑装得下而做的压缩**，比如「一个机制包打天下」「概念越少越好」
这类设计上的统一性要求。

下面四项**不在放宽之列**。它们看着像可读性，其实是可验证性或者信息量：

| 项 | 为什么留下 |
|---|---|
| 命名 | 命名是信息，不是装饰。`fn f(a: u64, b: u64)` 比 `fn commit_txn(gen: Generation, root: Logical)` 少了一整层语义，模型也补不回来。细则见下面「函数名不限长度，但不用缩写」 |
| 函数职责单一 | 一个函数做一件能单独验证的事。长度按这个定，不按屏幕高度定 |
| 路径数有限 | 全覆盖这段代码要多少个用例？答得出而且有限，就能验。注意量的是路径数，不是嵌套层数，见下面「嵌套层数本身不设限」 |
| 约定一致 | 约定不一致会让机器检查失效。这和「设计统一性」是两回事，别混 |

判据还是那一条：这条规矩让验证更容易，还是只让人看着舒服？
上面四项都属于前者，所以留下，但理由要改写成验证和信息量，不再挂在「可读」上。

### 函数名不限长度，但不用缩写

长度不设限，理由和「函数要短」那条一样：它量的是行宽和人的短期记忆。
多十个字符换一层语义，对机器来说永远划算。

**缩写是纯亏**：省下几个字符，丢掉的是语义，而模型补不回来——更糟的是它会瞎补。
`cnt` 在一处指块数、另一处指重试次数，检索到其中一处的模型不会说「我看不懂」，
它会按最常见的那个意思往下推。
例外只有一种：术语表里登记过的领域缩写（`lba`、`crc`）。它们是专名，
判据是「有没有一处权威定义」，不是「大家看不看得懂」。

**判据：不看注释、不看调用点，光看这个名字，能不能说出它做什么、不做什么。**

好名字还该带上**前置条件和作用范围**，等于把一部分契约提到签名上：

| 名字 | 它约束了什么 |
|---|---|
| `write_node` | 什么都没约束：写到哪、验没验、能不能中途崩溃，全靠读实现 |
| `append_verified_node_to_journal` | 追加而非覆盖、入参已验过、落点是日志区——三条前置条件写在名字里 |

**类型能表达的交给类型，类型表达不了的写进名字，都别写进注释。**
注释会和实现脱节，名字和类型不会。

这条机器检不了，所以它是 review 时看的，不是门禁项（`show-me-test.md`
「门禁能证明什么，不能证明什么」）。起不出这样的名字，多半说明这个函数
做的事本身还没想清楚。

### 嵌套层数本身不设限

「嵌套不超过三层」这类规矩量错了东西。真正决定能不能验的是**路径数**：

| | 路径数 | 可测吗 |
|---|---|---|
| 12 层 `for` 遍历一个 12 维结构 | **1** | 完全可测，深度再大也无所谓 |
| 12 层独立 `if/else` | **2¹²** | 测不完 |
| 3 层独立 `if/else` | 8 | 勉强 |

循环嵌套几乎不增加路径，条件嵌套按指数增加。旧规矩把两者一起限死，
是因为人读起来都一样费劲——那是人的约束，不是验证的约束。

所以层数随意，只要满足两条：路径数说得出、而且有限；每一层的含义是显式的。
第二条是说每层的迭代对象要有名字、有类型，不能是 `a[i][j][k][l]`。
那种写法的毛病不是深，是不带信息，和「命名是信息」是同一条。

### 一个例子：语义该放在哪

同一件事的三种写法，从差到好：

```rust
// 一、语义在注释里 —— 传统做法，最差
// dim0: 民族  dim1: 性别  dim2: 年龄段
pop[i][j][k]

// 二、语义在名字里 —— 以往被嫌啰嗦，机器很喜欢
num_china_people[han][woman][teenager_18_to_24]

// 三、语义在类型里 —— 最好，写错维度直接编译不过
num_china_people[Ethnicity::Han][Gender::Woman][AgeBand::T18to24]
```

第一种是为了让人脑装得下而做的压缩：名字缩到最短，语义挪进注释。
在行宽和屏幕都有限的年代这么写是合理的。但注释会和代码脱节，名字不会——
因为名字就是代码。

第二种过去常被嫌「太长，一眼就看出是三维数组，何必写全」。那是人的审美。
对机器它是纯赚：每一维都自己说明自己，**不看上下文就能判断这次访问对不对**。

第三种把信息从「能读」推到「能检」——维度写反了根本编译不过。
这和 `machine-first.md` 里「宁可用类型让非法状态写不出来，也不写注释解释约束」
是同一条，也和这个项目已经定下的 newtype 纪律（逻辑地址、物理地址、代号各是一个类型）同源。

**判据**：这段语义放在注释里、名字里、还是类型里？
**越往后越好，因为越往后越难与实现脱节。**

## 推论：人的注意力该花在哪

人的注意力是这套体系里最贵的东西，所以别花在读代码上——那件事交给模型。

该花在这四件机器判不了的事上：

1. **这个测试测的是不是对的东西**
2. **这条不变量本身对不对**
3. **这个决策的依据成不成立**
4. **要不要接受这个取舍**

这四件都不用通读实现，但都要求**给人看的那一面对人友好**。

所以门禁的输出、kb 的结论、决策记录、失败信息，都要为人优化，而且比过去更用力——
因为它们现在是人唯一会看的东西。代码写得难读可以接受，这四样让人判断不了不行。

## 两条轴的分界线

> **Gate proves evidence requirements, not semantic correctness.**

这句话就是分界：机器证明证据够不够，人判断语义对不对。
往下是实现面，往上是审核面。

## 这两面各写在哪

| 面 | 写在哪 |
|---|---|
| 实现 | `machine-first.md`、`kb-discipline.md`，以及各项目自己的设计纪律 |
| 审核 | `show-me-test.md` 的 howto 要求、`design-doc-discipline.md`、决策记录的依据要求 |
| 分界 | `show-me-test.md`「门禁能证明什么，不能证明什么」 |
