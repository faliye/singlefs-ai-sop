# 准入铁律：Show me test

> **Make every submitted patch review-worthy.**
>
> 让每一份提交都值得被 review。
>
> **Contribution throughput may be unbounded; acceptance throughput is evidence-bound.**
>
> 投稿吞吐可以无限，接收吞吐受证据约束。

**这是本工程与 Linux 内核最大的不同，也是最重要的一条规则。**

## 门禁是抬地板的，不是筛人的

第一句是目的，第二句是理由，两者的次序不能颠倒。

**门禁存在的目的不是把谁挡在外面，是把每一份提交抬到「值得花人的时间去看」那条线上。**
机械的部分（有没有测试、声明与实测符不符、文档与实现同不同步）由脚本做完，
人的注意力才腾得出来，用在只有人能判的地方——**这个测试测的是不是对的东西**。

第二句说的是为什么必须这么做：不论提交从哪来，供给这一侧只会越来越大，
而人的 review 带宽没有变。**能跟着扩展的只有证据。**

反过来说，一份没带证据的提交，消耗的是别人的时间去问「你验过吗、怎么验的」——
门禁把这一轮来回提前到提交者自己的机器上，**对双方都是省事，不是刁难**。

## 判据是测试

**patch 的去留由自动化验证决定。** 每一个 patch 都应当经过严格测试；
**欢迎每一份认真测试、负责任的提交。**

门禁过就是过，不过就是不过——这对提交者是保护：
你的 patch 能不能进，取决于它验证得够不够扎实，而不取决于你是谁。

## 没有测试的 patch 一律不收

**改了 `crates/*/src/` 就必须带测试。** 没有例外，没有「这个太简单了」，
没有「下个 patch 补上」。文档和脚本改动除外。

由 `scripts/gate.sh` 强制，不靠自觉。

## 新增的测试必须先证明它会红

**每个「验证」都必须能失败。** 写完自问：如果这段代码真的坏了，我的检查会不会报警？

正确做法：**先把被测代码改坏，确认测试变红，再改回来。**
不能证明会红的测试等于没写。

脚本验证不了这一步（它只能看出「有没有测试」），所以**在 commit message 里
写明你是怎么确认它会红的**——改坏了哪一行、看到哪个断言失败。写不出来就是没做。

## 踩过的坑要做成会失败的检查，不要做成提醒句

一句「注意别在 X 时候做 Y」拦不住手敲命令，**一个在那时直接拒绝执行的检查才拦得住**。
新发现的坑，第一反应是「这条怎么变成门禁里会红的一项」，而不是「这条写进哪个文档」。

## 最终判据是 QEMU/KVM 压测

单元测试和模型对拍是快速反馈，**不是准入标准**。
准入标准是在 QEMU/KVM 里跑真实负载 + 崩溃注入，跑完 checker 全绿。

## 门禁不许假装通过

未实现的门禁阶段必须**显式报告为未实现**，不许静默跳过。
一个悄悄没跑崩溃测试的绿色门禁，比红色门禁危险得多。

同理：**跑批脚本不许吞掉单轮失败**（`|| true` 之类），输出路径也不许跨轮复用。
两件事凑一起，失败的那轮会安静地拿上一轮的输出充数——看上去一切正常，只是数字不动。
判据是「这份输出能不能证明是这一轮产生的」：跑前删旧输出，跑后认一个本轮才可能出现的完成标记。

# 门禁能证明什么，不能证明什么

> **Gate proves evidence requirements, not semantic correctness.**
>
> 门禁证明的是证据要求被满足，不是代码语义正确。

**这条是题眉「让每一份提交都值得被 review」的必要配重。** 没有它，「门禁全绿」会被读成「代码是对的」，
而那正是本工程最想避免的那种静默错误。

## 能通过全部门禁、却仍然是错的

| 情形 | 门禁为什么看不见 |
|---|---|
| 测试测的是实现而不是契约 | 它只数「有没有测试」，不判「测得对不对」 |
| litmus 声明本身写错了 | 声明 Sometimes、实测 Sometimes → 判「符合」。**除非有对照组**，否则什么也没证明 |
| 不变量本身是错的 | checker 会忠实地检查一条错误的规矩，而且全绿 |
| 覆盖的不是出问题的那条路径 | 覆盖率不是正确性 |
| 设计层面就错了 | 门禁完全够不着这一层 |

## 推论

1. **门禁绿不等于可以不看代码。**
   它的价值是把人从「找有没有测试」里解放出来，
   去看**「测试测的是不是对的东西」**——那才是只有人能做的部分。

2. **语义正确性住在 `kb/decisions.md` 和 `kb/invariants.md` 里，不住在门禁里。**
   门禁只保证这两样东西**被写下来、被实现、且与代码同步**；
   它们写得对不对，靠人。

3. **门禁是下限，不是上限**（`rules/sop-first.md`）。
   它保证没有人低于某条线，不保证任何人达到了正确。

4. **未实现的阶段要一直显式列出。**
   缺一个验证手段，就等于有一整类错误从没被看过。
   `gate.sh` 每次都打印这份清单，就是不让人把「过了」当成「验过了」。

## 为什么是这条规矩

**贡献吞吐正在变成无限，而人的 review 带宽没有变。**

不论提交从哪来——更多的人、更好的工具、更强的自动化——供给这一侧只会越来越大。
「靠人逐行读代码」这个模式跟不上。唯一能跟着扩展的是**自动化验证**：
它不关心 patch 从哪来、写得多漂亮，只关心跑不跑得过。

## 把判据放在证据上，正是为了不按来源区别对待

**按来源分类审查才是歧视，而且它还不管用。**

一旦按提交者是谁来决定审查强度，
就等于用身份代替了证据——**而一个 patch 不会因为作者是谁而变好或变坏**。
身份是个糟糕的预测变量：它既冤枉认真的新来者，也放过随手提交的熟人。

证据不同。它对所有人是同一把尺子，而且**提交者自己就能提前量**——
在发出去之前跑一遍门禁，就知道自己站在哪。这是身份判据永远做不到的。

所以本工程**不按来源设类别**，也不为任何一类单列规矩。
只有一类划分：**带着证据的提交，和不带的。**

**所以门禁的质量就是这个工程的上限。** `scripts/` 比任何一个 crate 都重要。
